# 0006. UUIDv7 identifiers and offset pagination

- **Status:** Accepted
- **Date:** 2026-10-05

## Context

Todos need unique IDs generated by any replica without coordination, and
`GET /todos` must not return an unbounded result set.

## Decision

**IDs: UUIDv7** (RFC 9562), generated in the service layer.

- Generated independently on any replica, with no database round-trip or
  sequence.
- Not guessable or enumerable like auto-increment integers.
- Time-ordered prefix, so new rows append to the end of the primary-key
  B-tree index instead of scattering like UUIDv4.

**Pagination: `limit` / `offset`** with a response envelope
`{items, total, limit, offset}`.

- Default `limit` 20, maximum 100, so no request can fetch an unbounded
  result.
- Deterministic order `ORDER BY created_at, id`, backed by an index on those
  columns. The `id` tiebreaker keeps pages stable when timestamps collide.
- `total` and the page are read in one `REPEATABLE READ` read-only
  transaction, so they are consistent with each other.
- Timestamps are stored at microsecond precision in UTC (PostgreSQL's
  precision), so values round-trip exactly.

## Alternatives considered

- **Return all todos as a bare array:** matches "retrieve all" literally, but
  it is unbounded and can't be extended with metadata without a breaking
  change.
- **Cursor (keyset) pagination:** faster for deep pages and stable under
  concurrent inserts, but harder for clients to use (no random page access, no
  total). Listed as a future improvement.
- **Auto-increment IDs:** need coordination through the database and are
  enumerable.

## Consequences

- Deep offsets get slower (`OFFSET n` scans n rows), and inserts between page
  requests can shift items across pages. Both are acceptable at this scale.
- The envelope can carry future metadata (e.g. a `next_cursor`) without
  breaking clients.
